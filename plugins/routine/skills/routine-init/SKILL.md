# Инициализация Routine

Твоя цель — сделать проект понятным общему скиллу сопровождения, сохранив его собственные процессы. Общайся по-русски. Результат — редактируемый `.harness/workflow/project.yaml`, согласованные опорные файлы и ясный перечень того, что настроено, сохранено или осталось неизвестным.

Это исследование и согласуемая адаптация, а не установка одинакового процесса всем проектам. Создание YAML не разрешает переделать правила, внедрить новые гейты или написать универсальный ревьюер вместо проектного.

## Источники и границы

Различай каталог установленного плагина и рабочий репозиторий. Ссылки ниже разрешай относительно этого SKILL.md; пути внутри project.yaml — относительно корня целевого репозитория. Убедись, какой репозиторий выбран, по доступному контексту и Git. При нескольких возможных проектах уточни.

Прочитай [контракт проекта](../../references/project-contract.md). Для работы с ревью используй [контракт ревью](../../references/review-contract.md). Шаблоны перечислены в [каталоге](../../templates/README.md); загружай нужные, не весь пакет.

Исследуй входные инструкции проекта, индексы документации и правил, существующий `.harness`, `.zcode`, `.cursor`, скрипты package/build и CI. Начни с индексов и точечных чтений. Не собирай секреты из `.env`, credentials, токенов и профилей; настройки подключения не входят в YAML.

Установи по источникам:

- какие документы являются принятыми правилами, какие — описанием текущей реализации или предложениями;
- какие проверки существуют, когда нужны, где выполняются и чем подтверждается успех;
- какие роли, скиллы и команды уже проводят ревью, что они реально проверяют и какие действия запускают;
- какие Jira/GitLab-настройки уже известны и какие решения нужно уточнить у пользователя.

Наличие команды не доказывает её успешное выполнение. Прочитай вызываемые скрипты настолько, чтобы увидеть режим watch, autofix, изменение БД, запуск сервисов и другие существенные эффекты. Не запускай весь pipeline ради заполнения YAML. Условие выбора профиля и существующий классификатор изменений сохраняй в проектных инструкциях, не выдумывай собственную замену.

## Решения пользователя

Предложи конкретный план по артефактам: найденное → изменение → причина. Для каждого набора правил спроси, что делать: **создать / дополнить**, **структурировать без изменения смысла**, **оставить как есть**. Вопрос можно объединить для нескольких наборов, но согласие на один не распространяется на остальные. Согласование из текущего разговора сохраняет силу.

Правила, выведенные только из наблюдаемого кода, — предложения до принятия пользователем. Конфликт между документами, проектным законом и общим форматом вынеси на решение; не переопределяй молча. Например, существующий `.harness` может требовать собственный README, другой формат конфигурации или хранение общих ролей вне него. Покажи совместимое дополнение либо конкретное исключение для согласования.

Выбор ревью — отдельное решение: использовать существующее, адаптировать, создать проектную инструкцию либо оставить `review.executor: null`. Оцени соответствие цели: аудит архитектуры, ревью плана и ревью diff MR не взаимозаменяемы. Не выдавай существующий файл команды Cursor за исполняемую команду ZCode.

Если чего-то нет, подготовь содержательные черновики по шаблонам. До записи покажи выбранные пути и существенные изменения. Не делай второй раунд одобрения, когда пользователь уже явно согласовал эти конкретные изменения. При полном отказе закончи без записи; частичный отказ не препятствует согласованной части.

## Что записать после согласования

- Заполни [project.yaml](../../templates/project.yaml) реальными значениями. Не используй адреса и команды из учебного примера как defaults. Неразрешённое оставь null / пустым и объясни влияние.
- Существующие документы подключи ссылками. Создавай индекс, наборы правил, проектное ревью и отчёт инициализации только в согласованном объёме, по соответствующим шаблонам.
- При создании ревью предпочтителен выбранный проектом исполнитель. Допустимый простой вариант — проектная инструкция для отдельного `general-purpose` подагента; она должна содержать конкретные критерии проекта и передаваться вместе с форматом результата из плагина. Место инструкции согласуй с правилами проекта.
- Не копируй весь пакет шаблонов и общие скиллы в `.harness`. Не меняй код приложения, CI, коммиты, ветки или push.

При повторном запуске сравни текущие настройки с найденным состоянием. Сохрани ручные поля, комментарии YAML, принятые исключения и прежнее решение «оставить». Предложи дельту; не заменяй файл целиком пустым шаблоном и не сбрасывай настроенный executor.

## Подтверждение результата

Перечитай записанное: пути, ссылки, команды, условия и способ ревью должны соответствовать исследованному проекту. Проверка структуры не является проверкой выполнения команд. Если реальные запуски или тест ревью не были частью согласованного запроса, отметь их как непроверенные.

В итог включи точные созданные / изменённые файлы, оставленное без изменений, решения пользователя и оставшиеся вопросы. Примени [шаблон инициализации](../../templates/initialization.md), если согласовано сохранение отчёта. Дай короткий пример вызова routine-assist для первой задачи этого проекта.
