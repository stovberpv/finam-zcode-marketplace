# Проверки и доказательства

Определи, какие проверки нужны именно для текущего результата. Оформление задачи не требует прогонять весь репозиторий. Заявление готовности должно опираться на применимые требования и критерии задачи.

Читай `quality.checks` и указанные проектные инструкции. Проверка может быть командой или ручным сценарием, включая существующий выбор профиля проекта. Условие `required_when` оценивает агент по изменениям и цели, а не новый движок Routine.

Перед запуском учти реальные эффекты команды. Имена `check`, `test`, `format` не гарантируют read-only: скрипт может писать baseline, делать autofix, сбрасывать БД, устанавливать зависимости или обращаться к реальной сети. Скилл сопровождения не исправляет код и не меняет baseline; необходимые изменения передаются проектному исполнителю. Если запуск зависит от него, явно отметить препятствие, не обходить принятое правило.

Для каждого результата зафиксируй исполнителя, команду / сценарий, cwd, среду, время и доказательство. Отделяй уже предоставленные результаты от новых запусков. Связывай их с commit / snapshot; при dirty worktree одного SHA недостаточно. Не выдавай общий CI pipeline на другой ветке за проверку текущих изменений.

Статусы:

| Статус | Значение |
|---|---|
| PASS | Проверка действительно выполнена успешно для указанной версии |
| FAIL | Выполнена и выявила проблему |
| BLOCKED | Запуск / завершение невозможно по конкретной причине |
| NOT_RUN | Не выполнялась |
| N/A | Неприменима по конкретному правилу проекта |

Пропуск тестов, пустой suite и отсутствие конфигурации не означают PASS. Ревью не заменяет запуск тестов; успешные команды не доказывают выполнение всех функциональных критериев. Применяй [шаблон отчёта](../templates/quality-report.md), не стандартный чек-лист lint/typecheck/tests/build для всех технологий.
