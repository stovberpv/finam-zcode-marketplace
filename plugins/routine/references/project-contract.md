# Контракт проекта · schema_version 1

Настройки лежат в `<repository>/.harness/routine/project.yaml`. Это отдельный каталог системы, не корень всей `.harness`. Все локальные `path`, `source`, `instructions_path`, `cwd` и `result.path_pattern` разрешаются относительно **корня репозитория**. Каталог установленного плагина никогда не является этой базой.

## Поля

| Поле | Назначение |
|---|---|
| `schema_version: 1` | Структура конфигурации |
| `standard_version: "0.1"` | Версия общего формата отчётности |
| `project.id`, `project.name` | Устойчивое имя и читаемое название проекта |
| `jira.site_url` | Jira-сайт |
| `jira.defaults.project_key`, `epic_url`, `parent_url` | Начальное размещение новой работы; parent необязателен |
| `gitlab.repository_url`, `remote`, `default_target_branch` | GitLab-проект, локальный remote, default нового MR |
| `references.documentation[]` | `{id, path, description}` — источники контекста |
| `references.rules[]` | `{id, path, scope, status}` — `accepted` или `draft` |
| `quality.checks[]` | `{id, purpose, required_when, execution, success, evidence}` |
| `review.executor` | Исполнитель ревью или `null` |

У проверки `execution.kind: command` задаёт `cwd` и `command`; `kind: manual` — `instructions_path`. `required_when` и `success` — содержательные условия для агента, не исполняемый DSL. Для динамического проектного классификатора допустима ручная инструкция, описывающая существующий выбор GATE_COMMAND; не превращать динамический результат в навсегда захардкоженную команду. Команда должна быть исследована, а не угадана по имени.

У исполнителя ревью: `kind`, `source`, `invocation: {mode, target, instructions}`, `result: {format, delivery}`. Контракт и допустимые режимы — [review-contract.md](review-contract.md).

Пустой шаблон содержит null и пустые списки; это неизвестное / ненастроенное, не успешное подключение. В рабочем конфиге заполнять только подтверждённое. Пустые проверки не означают PASS. `draft` правила не применять как обязательные. Нет полей для секретов, установки интеграций, текущей задачи или глобального последнего отчёта.

## Источники истины

- Намерение и согласованные изменения объёма — из запроса и разговора.
- Актуальные родитель, эпик и проект существующей задачи — из Jira.
- Текущая ветка и локальные изменения — из Git; source/target и опубликованный diff существующего MR — из GitLab.
- Defaults YAML помогают новой работе, но не отменяют актуальные связи. Если defaults устарели, задача сопровождается по живым данным; изменение defaults — отдельное решение.
- Источники правил, проверок и проектного ревью — по ссылкам конфига с учётом входных инструкций репозитория. При конфликте показать его, а не изобретать универсальный приоритет.

## Опорные файлы без обязательной миграции

В каталоге Routine могут быть `index.md`, `rules/<name>.md`, `review.md`, `initialization.md`. Это варианты для недостающих документов, не требование создать все. Существующие `.zcode/rules`, `.cursor/rules`, README, CONTRIBUTING, docs и исполнители могут остаться на месте. Формат индекса или правило хранения `.harness` конкретного проекта учитывать при согласовании.

Общие скиллы, шаблоны и этот контракт поставляются плагином; не создавать их расходящиеся копии в каждом проекте. Разрешено создавать проектные документы по общему шаблону. Не копировать в проект README плагина как проектные правила.

## Состояние работы

Задача, ветка, MR и решения относятся к текущему чату / рабочему каталогу. Если нужен файл результата — отдельный каталог на work_id; при согласованном использовании `.harness/routine/local/` исключить его из Git. Нельзя использовать один `latest-review.md` для всех параллельных работ.

Повторная инициализация сохраняет ручные поля, комментарии YAML, текущего исполнителя и принятые решения. Структурирование не меняет содержание правил без отдельного согласования. Если версия конфига новее известного контракта, не перезаписывать его шаблоном v1; обозначить несовместимость и подготовить согласуемую миграцию.
